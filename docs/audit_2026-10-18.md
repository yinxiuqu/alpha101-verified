> 来源：一位使用者对仓库做的独立审计（含复现证据）。本文**逐条核实**并给出结论/优先级/计划。

## 一、先回答一个关键问题：换「后复权」能根治增量更新问题吗？

**不能，而且「换」这个动作本身不需要——因为默认已经是后复权。**
`alpha101v.adapters.mongo.load_panel(adjust=...)` 的默认值就是 `"hfq"`（`mongo.py:181`）；
`qfq` 仅供展示（全样本使用含前视），`none` 会出假跳空。

**真正的问题不在 hfq/qfq 的选择，而在当前 hfq 的实现方式：**

| 位置 | 现状 | 后果 |
|---|---|---|
| `adapters/adjust.py:168` | `prev_close = series.iloc[position - 1]` | 用**面板里的上一行**当前收：若中间有停牌（NaN），除权事件的因子被静默当 1.0 ⇒ **同一股票单独请求 vs 批量请求结果不同**（审计实测 000651：单股 56.2956 / 多股 51.9021）|
| `adapters/adjust.py:184-185` | `tail = factors.iloc[-1]`，再整体除 tail | 复权**锚在面板最后一行** ⇒ 同一日期的复权价**随窗口起点变化**（实测比值 2.108128）|

⇒ **正确做法是「按股票自身的 xdxr 全历史 + 固定锚」计算累计复权因子**，而不是「按面板的行位置」：

1. 每只股票的累计因子只由**它自己的 xdxr 全历史**决定（与请求了哪些股票、窗口从哪天开始无关）；
2. 除权日的参考价用**该股票自己在该日期之前最近一个有效收盘**（跳过停牌），而不是 `iloc[position-1]`；
3. 锚点固定（例如统一锚到「该股票最后一个有效交易日」，或提供一个显式的 anchor 参数），使复权价**幂等**；
4. 有了这样的因子表，**增量更新天然安全**：任意窗口/批次取同一 (股票,日期) 都得到同一个值。

也就是说：**hfq 是必要的（且已是默认），但必须从「面板锚定」改成「xdxr 历史锚定」才有意义。**

## 四、采纳的一条方法论建议：补第 7 层验证

审计者指出：现有 L1–L6 都在「单次调用、固定窗口」下验证，**没有一条验证「结果与调用方式无关」**——
而 A、B 两个 bug 恰好都落在这个盲区。建议采纳为 **L7 调用方式不变性**：

> 同一 (股票, 日期)，无论 ① 单独请求还是与 N 只一起请求；② 窗口起点早或晚；③ 分几次增量算，
> 结果必须**逐位相同**。

测试成本极低（几十行：同一面板切窗口/切批次/拼接后重算，逐点比对），却同时挡住 A 与 B。
**这一层对「可验证」这个定位的说服力可能比 L6 统计更高**——我会把它写进 `docs/verification.md` 的门槛清单，
并在修 A/B 时**先写 L7 测试再改实现**（红-绿）。

## 五、⚠️ 对上一版结论的更正（作者实测反馈，2026-10-18）

### 5.1 撤回「用 xdxr 构造后复权」

上一版我写「按股票自身 xdxr 全历史构造累计复权因子」——**这条是错的，撤回** ✗。
审计者的实测：**用 xdxr 自建后复权，送转股会偏 8–40%**（xdxr 里的送转/配股口径与供应商的
复权因子不是一回事）。

**决定性事实（我刚查库确认）**：库里存在供应商维护的复权因子表 **`stock_adj`** ——
**1824 万条** `(date, code, adj)` 文档（样例 `000003 / 1991-07-03 / adj=0.2577`），
而本仓库的适配层**根本没有读它** ✗（`adapters/adjust.py` 全篇基于 `stock_xdxr` 自建）✓。

⇒ **正确做法**：复权因子**直接取 `stock_adj`**（供应商已处理送转/配股/分红），
不再自建；这也解释了 A/B 两个 bug 为何会出现（自建逻辑要自己锚定，锚一歪就漂移）。

### 5.2 锚的纪律：每次重算、绝不跨运行持久化

审计者的实测教训（值得抄进纪律）：

> 一开始把**锚值持久化**了。结果一夜之间 **69 只股票新除权**，锚值最大偏 **5.77%** ⇒ 历史整体漂移 ✗。
> 改成**每次运行都用当前快照在 `ref_date` 上重算锚**后，与旧库对比相对差回到 **~6e-8**
> （float32 半个 ULP）✓。

**纪律（写入 `docs/verification.md` 的 L7 旁注）**：

* 锚**只在运行时重算**，**绝不从上次运行的产物里读回来当输入**；
* 锚表可以**入库**，但只作**审计/对比**用途，**不得作为计算输入**（这是「可对比」与「可复现」的分界）；
* `ref_date` 必须显式记录在 manifest 里，便于复算。

### 5.3 采纳：`--check-anchor-drift`（把静默漂移变成明确告警）

**答：要，请加上** ✓ —— 它成本低、正好补上「杜绝以后出现增量更新问题」的最后一块。
设计以「三分类」为准，且必须**只读、可离线、可疑即非零退出**：

```
每次 build/update 成功后，在 manifest 里写入：
  ref_date, anchor_sha256, 以及每只股票的 [anchor_value, latest_event_watermark]

下次运行：重算锚后逐股比对
  · 锚未变                          → OK（正常）
  · 锚变了 且 该股有新的 xdxr 事件   → OK（良性：G 不变，只是新增除权）
  · 锚变了 但 该股没有新事件         → ⚠️ 疑似供应商修正了历史数据
                                        → 报警 + 非零退出 + 建议重建因子库
```

落地要求：
1. **只读**：只比对，不改任何数据；
2. **不把锚当输入**：对比用的是「本次重算的锚」vs「manifest 里记录的锚」；
3. **可疑即失败**：非零退出码（CI/发布前脚本可以直接用）；
4. 输出要能定位：列出可疑股票代码、锚偏差百分比、以及该股最后一条 xdxr 事件日期。
